## Evidence and decisions

**E1 — synthetic redaction fixture.** The GitLab-shaped string originates in the original redaction tests (foundation merge `aa16a99`), contains an obvious consecutive-alphabet placeholder, and is asserted as input to be scrubbed. Its exact value occurs across all reachable Git history only in `tests/unit/redact.test.ts` and its `.gitleaks.toml` allowlist. No authentication attempt was made with it. Gitleaks extends every default rule; its allowlist uses `condition = "AND"`, the anchored single test-file path and six anchored exact fixture values. Nothing broadly excludes GitLab tokens or all tests. Gitleaks v8.30.1 scanned all 139 reachable commits with zero findings. Three isolated synthetic controls verified: the fixture at the intended path passes; the same value outside that path is detected; a different generated token-shaped value inside the test path is detected. This is scanner evidence, not proof that every possible credential format can be detected. Preserve the useful redaction tests and classify this alert as a false positive/safe fixture; no real credential was identified and no rotation is indicated by this evidence.

**E2 — explicit native builds.** CI and Docker now install using `pnpm install --frozen-lockfile --ignore-scripts`, then explicitly run `pnpm rebuild better-sqlite3 esbuild`. This retains the existing two-package `onlyBuiltDependencies` allowlist and pinned pnpm 9.15.9/package versions/lock integrity. No lockfile/dependency change or package-manager upgrade. Those two approved packages still execute trusted dependency build code; this is a bounded approval, not a claim that all scripts are disabled. Docker's compiler/dev dependencies stay in discarded build stages, build receives no production secrets, runtime runs as node with no package managers. A fresh worktree dependency install and explicit rebuild succeeded; full check/build and Docker verification are reported on the PR.

**E3 — Playwright browser provisioning.** `pnpm exec playwright install --with-deps chromium` resolves the installed, exact pinned `@playwright/test` 1.64.1 from the frozen lockfile, not an unversioned `npx` download. Playwright's matching browser revision and OS dependencies are installed in a disposable GitHub-hosted Ubuntu job; this is deliberate browser test provisioning. The job token has contents-read only, checkout credentials are not persisted, no deployment secrets are passed. The action versions are SHA-pinned. Browser downloads are still an upstream supply-chain trust boundary; avoiding dependency install hooks does not eliminate that deliberate trust. Keep Chromium/axe tests and review this instance as safe/false positive for the broad installation-script rule.

**E4 — least-privilege image publishing.** Workflow defaults retain only contents-read. Both build-scan-push (GHCR login, immutable image push/tag restoration) and promote (GHCR login, moving tags) explicitly request contents-read/packages-write. Checkout needs repository read; GHCR pushes need packages-write. Build provenance/SBOM is attached by BuildKit to the image, not the GitHub attestations API. The reusable Release Please caller already grants those scopes at its publish-image job, while its workflow defaults are empty. Permissions can only be maintained/reduced across reusable calls. Other release jobs already scope write permissions to the jobs that need them; no unrelated permission change. Actionlint/shellcheck and existing release-image helper tests validate structure/logic. Publishing/promotion itself was not executed because creating releases/publishing images is outside this task's authorization.

**E5 — test-only Git invocation trust boundary.** Each of the 18 call sites below was checked individually. All use a constant executable name and argument arrays with no shell. The HTTP backend uses the same trusted process environment captured at test-module load, never request-supplied PATH; request fields become CGI metadata, not an executable/shell string. Repository/branch/file fixtures come from test code and run under fresh temporary directories. The server listens on 127.0.0.1 with an ephemeral port. CI runs on a disposable GitHub-hosted Ubuntu runner with contents-read only, no production tokens/deployments, and SHA-pinned setup actions. This helper is only imported by integration tests; Docker excludes the entire tests directory and production tracing output removes tests. Local developers must trust their own executable environment, just as they trust Node/pnpm and the test code itself.

An attacker who controls the test process PATH or checked-out executable test code already controls that same test job; these calls add no production entry point or privilege boundary crossing. Resolving an absolute Git path from that same PATH would not establish authenticity. Requiring a new trusted-path setting or hardcoding an OS path would add cross-platform setup and failure modes without reducing the demonstrated threat. Retain the working shared helper and recommend safe/false-positive dispositions for these test-only instances. This rationale does not apply if the helper moves into production, a privileged/shared runner, or a process accepting an untrusted executable environment; reassess then. All existing Git integration tests remain enabled.
