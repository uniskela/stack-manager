# v0.6.0 — automatic fetch, deployment routing and dashboard

**Status:** proposed implementation plan (2026-10-20)  
**Tracking:** [parent #51](https://github.com/uniskela/stack-manager/issues/51)  
**Current completed foundation:** PR #2–#4; Git workflow shipped in v0.5.0.  
**Sequence:** Small independently reviewable PRs; keep planned PR #5 deployment routing as the core feature. v0.6.0 is tentative (Release Please owns numbering).

## Goal

A source-centric dashboard that stays fresh in the background, detects verified external changes and optionally triggers the deployment webhook of **only** affected stacks. Eliminate routine fetch clicks without converting Stack Manager into a Docker runtime manager.

### Non-goals

- No Containers / Images / Networks / Volumes pages, direct container controls, Docker socket, runtime health claims or auto-repair.
- No merge/rebase/force push, no silent draft cleanup and no destruction of unpushed retained refs.
- Do not start PR #6 secrets providers, PR #7 runtime watch or PR #8 PWA early.
- No Redis, external scheduler or extra service unless measured scale requires it.

## Slice 1 — automatic repository fetch [#52](https://github.com/uniskela/stack-manager/issues/52)

**Start here.** Use the existing `GitRepositoryService`, `repository_sync` job handler, persistent queue, dedupe keys and per-repo Git locks.

1. Add repository-scoped fetch policy: `autoFetchEnabled` (default true) and interval (default 15 min, bounded range). Decide exact settings UI/API shape separately from scheduler. Existing repos should get safe schema defaults.
2. Add durable `lastSyncAttemptAt` (and optionally `lastHeadChangedAt`) distinct from `lastFetchedAt`, which currently records successful fetch. Due predicate uses attempted-at + policy interval, not just successful fetch time; failures must not generate tight retry loops.
3. In long-running server boot, start a minute-resolution scheduler only if worker enabled. Iterate workspaces/repository connections via ports. Queue due syncs using existing `repository_sync:<id>` key; do not call `git` on HTTP/dashboard render. Stop scheduler during graceful shutdown; bootstrap catch-up after restart.
4. When a sync is queued, dedupe against pending/running jobs. Detect/avoid stale locks and report failures with backoff through the existing worker. Keep manual Fetch now available.
5. After **confirmed** local Git push success, enqueue a refresh of the source snapshot (do not clear drafts or retained commits). Watch for interaction with Git mutation locking; enqueue after lock release.
6. Routine unchanged scheduled checks should not flood audit or create duplicate stack discovery rows. Keep audit for failures/state changes; ensure last-checked state remains visible in repository UI.
7. Add deterministic-clock tests: first-run, not yet due, interval boundary, success, failure backoff, duplicate scheduler tick, worker-disabled, restart, pending/running, race with manual fetch, protected drafts/retained refs, post-push refresh.

**Acceptance:** fresh commits appear without a button click after at most configured fallback interval; post-push refresh follows a successful push; no draft or unpushed commit loss; no repeated tight polling.

## Slice 2 — verified inbound forge webhooks [#53](https://github.com/uniskela/stack-manager/issues/53)

1. One inbound webhook per configured repository, with separate `webhookCredentialId` secret. Do not reuse clone/push PAT.
2. Add explicit GitHub/Gitea/Forgejo event-verification adapters. Authenticate **raw** request bytes with constant-time comparison, bounded request bodies and the provider's actual signature format; fixture tests are required before implementation. Check repository identity, tracked ref, event type, payload size, signature and delivery id. Fail closed on unsupported or missing signing mechanisms.
3. Persist accepted delivery IDs transactionally; webhook HTTP handler acknowledges only durable enqueue. Duplicate delivery must not queue a second deployment. Discard irrelevant branch/repository events with explanation.
4. Webhook signals a background fetch rather than assuming a payload-supplied list of paths is authoritative. Receiving webhooks must be safe without opening deployment bindings.
5. Document reverse proxy paths, provider setup and network/TLS needs. Do not expose secrets via client responses, logs or job payloads.

**Acceptance:** verified push accelerates fetch; unsigned/mismatched/replayed deliveries are rejected or ignored safely; GitHub/Gitea/Forgejo contract tests pass.

## Slice 3 — outbound per-stack deployment bindings [#54](https://github.com/uniskela/stack-manager/issues/54)

1. Explicit `DeploymentBinding` associated with a stack and provider `portainer-webhook` / `generic-webhook`; one binding per stack initially is acceptable if future model supports multiple. No folder-name inference.
2. Encrypt all secret-bearing webhook URLs and auth via existing credential service (do not store webhook token or secret URL plaintext in metadata or logs); redact structured audit/job events.
3. Provider interface returns `accepted` and HTTP/error metadata only; **not** `healthy`. Safe outbound transport: HTTPS, disabled redirects, connection timeout, host allowlist/network policy/SSRF checks including DNS redirects and rebinding. Private homelab endpoints require explicit existing private-network configuration.
4. Per-stack settings show masked provider, enabled state, deploy-on-push switch (default **off**), changed-file policy and last accepted/failure. Deliberate manual Deploy action with confirmation, authorization and audit, not available without binding.
5. Preserve existing Git commit workflow and offer separate manual deployment independent of auto-deploy status.

**Acceptance:** one stack can trigger its own configured deployment webhook without exposing credentials or implying runtime health.

## Slice 4 — changed-path routing and idempotency [#55](https://github.com/uniskela/stack-manager/issues/55)

1. Pure policy evaluator for each explicit Stack `rootPath`, `include`, `exclude` and `dependencies` as described in [routing design](../DEPLOYMENT_ROUTING.md). Give safe defaults that include compose/config paths and skip documentation-only changes.
2. Determine changed paths from trustworthy local Git revisions. Before deciding, compare previously processed source SHA to fetched head; handle multi-commit ranges, rapid sequential pushes, missing ancestors and rewritten/force-pushed histories explicitly (conservative skip + review, never blind deploy). Atomic checkpoint prevents missing changes when jobs coalesce.
3. Persist `DeploymentEvent`, delivery, routing decision and per-stack trigger idempotency. One trigger per relevant stack per source event; existing worker leases and acceptance recording prevent repeats where supported. After provider acceptance, never blindly re-fire on crash recovery; document residual uncertainty for Portainer webhook idempotency.
4. Same policy engine for eventual UI Commit → Push → Deploy and inbound Git push. Nonmatching branches, unknown stacks and unbound stacks never deploy.
5. Audit *why* a stack was deployed or skipped, retaining safe commit/path details but not secrets.

**Acceptance fixtures:** single stack change, README-only skip, shared dependency triggers two stacks, multiple commits, out-of-order delivery, replay, redelivery, worker crash, disabled binding, branch mismatch, failure recovery.

## Slice 5 — focused dashboard [#56](https://github.com/uniskela/stack-manager/issues/56)

1. Consolidated summary: stack count, drafts, sync problems, repository last checked/changed. Never infer running status or healthy containers from webhook acceptance.
2. **Needs attention** rows grouped by stack/repository. An outdated draft with an open draft is one action item; ordinary drafts are work in progress, not errors. Display sync failures with a concrete next action.
3. Remove Shortcuts that duplicate permanent sidebar navigation.
4. Replace full dashboard audit table with at most five meaningful recent activity items and link to Settings → Activity.
5. Optional Fetch now action and subtle automatic-refresh status; avoid live refresh loops, long rows and dense tables on mobile.
6. Add pure summary/attention tests, desktop/mobile Playwright and axe checks. Match existing app tokens and primitives.

**Acceptance:** no duplicate attention rows for the same stack, calm at 64+ stacks, accessible and understandable without needing to open multiple pages.

## Slice 6 — release gate [#57](https://github.com/uniskela/stack-manager/issues/57)

- Verify genuine Gitea push → sync → selected Portainer webhook acceptance in controlled homelab testing with opt-in deployment.
- Security test signature failure, replay, URL secret redaction, SSRF, credential rotation, duplicate jobs and malicious path/rule patterns.
- Migration/backups and rollback documented; new state defaults safe for existing v0.5.0 SQLite DBs.
- Update `docs/public/` and `docs/manifest.json` for UI/operator behavior, `docs/internal/` for architecture. Do not change existing public documentation slugs.
- Do not merge/release until tests and review are complete.
